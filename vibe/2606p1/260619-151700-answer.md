# GPX/KML 记录与轨迹地图数据源调研

## 结论

1. **只比较 GPX 与 KML 文件格式本身，现有代码下 GPX 更轻一些，但电量差异预计很小。**  
   主要耗电点不是 XML 写入格式，而是定位请求、定位重试、GPS 是否常开、上传/网络等。依据：定位请求由 `GpsLoggingService.startGpsManager()` 发起，GPS/网络 provider 均以 `requestLocationUpdates(..., 1000, 0, ...)` 取点；写文件只在通过过滤后的点上执行，位置在 `GpsLoggingService.writeToFile()`。

2. **默认是“一天一个 GPX 文件”，但不是固定只能一天一个。**  
   默认配置 `new_file_creation=onceaday`，文件名为 `yyyyMMdd`；也支持按月、每次启动、自定义模板。GPX/KML 共用同一个基础文件名，只是扩展名不同。

3. **GPX/KML 文件没有自动按保留期清理逻辑；有手动删除文件入口。**  
   手动删除入口是日志设置里的 `delete_files`，让用户在日志目录多选文件后逐个 `delete()`。本地轨迹缓存另有自动清理和手动清空，但它清的是 SQLite 表，不是 GPX/KML 文件。

4. **不建议把「轨迹地图」的主数据源改成每次从 GPX/KML 文件解析。**  
   当前 SQLite 本地轨迹缓存更适合作为地图数据源：按时间范围查询、可保留期清理、与 GPX/KML 开关解耦。GPX/KML 更适合作为导出/兼容格式，或作为一次性历史导入/回填来源。

5. **把本地轨迹缓存适配成 `FileLogger` 是更合理的最小改造，但不应把“轨迹地图 UI”本身变成 logger。**  
   本轮已新增 `TrackCacheFileLogger`，由它包装 `TrackCacheRepository.append(loc)`；`FileLoggerFactory.write()` 统一遍历 `getFileLoggers()`。由于「记录细节」页现在有显式的本地轨迹缓存开关，`TrackCacheFileLogger` 应放进 `getFileLoggers()`，并和其他输出目标一样参与详情页“记录到”展示。

6. **「记录细节」与「轨迹与地图」现在共用同一个本地轨迹缓存开关。**  
   `pref_logging.xml` 新增 `local_track_cache_enabled` 开关，使用同一组标题/说明文案；`pref_tracker.xml` 中原有开关也是 `local_track_cache_enabled`。关闭该开关后，地图 UI 仍可打开，但 `TrackMapViewFragment.loadPoints()` 返回空列表，不再展示缓存点。

## 依据

### 写入入口

- `FileLogger` 接口只要求 `write(Location)`、`annotate(...)`、`getName()`，并不强制必须写真实文件：`gpslogger/src/main/java/com/mendhak/gpslogger/loggers/FileLogger.java:24`-`30`。
- `FileLoggerFactory.getFileLoggers()` 在 `TrackerPreferenceHelper.isLocalTrackCacheEnabled()` 为 true 时加入 `TrackCacheFileLogger`，且放在日志目录检查之前，避免日志文件夹为空时影响本地轨迹缓存：`gpslogger/src/main/java/com/mendhak/gpslogger/loggers/FileLoggerFactory.java:47`-`56`。
- `FileLoggerFactory.write()` 与 `annotate()` 都统一遍历 `getFileLoggers()`：`FileLoggerFactory.java:107`-`115`。
- `TrackCacheFileLogger.write()` 包装 `TrackCacheRepository.getInstance().append(loc)`；`annotate()` no-op，避免注释流程重复插入点：`gpslogger/src/main/java/com/mendhak/gpslogger/tracker/cache/TrackCacheFileLogger.java:12`-`21`。
- GPX logger 是否创建取决于 `PreferenceHelper.shouldLogToGpx()`，默认 true；KML 取决于 `shouldLogToKml()`，默认 false：`PreferenceHelper.java:558`-`569`。
- 文件路径由日志目录 + `Strings.getFormattedFileName()` + 扩展名组成：`FileLoggerFactory.java:59`-`75`。
- 通过过滤后的定位点在 `GpsLoggingService.java:1104`-`1118` 更新 Session 后调用 `writeToFile(loc)`；`writeToFile()` 再调用 `FileLoggerFactory.write()`：`GpsLoggingService.java:1250`-`1260`。

### 本地轨迹缓存开关

- 「记录细节」新增的开关 key 是 `local_track_cache_enabled`，默认 true，标题/说明复用本地轨迹缓存文案：`gpslogger/src/main/res/xml/pref_logging.xml:27`-`32`。
- 「轨迹与地图」中原有开关使用同一个 key：`gpslogger/src/main/res/xml/pref_tracker.xml:10`-`15`。
- 读取该开关的实现集中在 `TrackerPreferenceHelper.isLocalTrackCacheEnabled()`：`gpslogger/src/main/java/com/mendhak/gpslogger/tracker/TrackerPreferenceHelper.java:50`-`52`。
- 轨迹地图加载点时先检查该开关；关闭时返回空列表，地图 UI 不受影响：`gpslogger/src/main/java/com/mendhak/gpslogger/tracker/ui/TrackMapViewFragment.java:338`-`345`。

### GPX/KML 写法差异

- GPX 写入使用单线程 executor，文件不存在时创建初始 XML，再用 `RandomAccessFile` seek 到闭合标签前追加 `<trkpt>`：`Gpx10FileLogger.java:59`-`70`、`220`-`246`、`278`-`360`。
- GPX 1.1 复用 GPX 1.0 写入流程，只替换命名空间/metadata，并把 bearing/speed 放到 `gpxtpx` 扩展：`Gpx11FileLogger.java:16`-`19`、`30`-`60`。
- KML 写入也是单线程 executor，文件不存在时创建初始 KML，再在尾部闭合标签前追加 `<when>` 和 `<gx:coord>`：`Kml22FileLogger.java:57`-`59`、`175`-`223`。
- 因此同一个点写 KML 通常文本更长；但相对 GPS provider 获取定位的耗电，格式差异不可从代码中量化。可确认的是：同时开启 GPX 和 KML 会多一次文件写入，比只开一种格式更重。

### 文件创建策略

- UI 配置项 `new_file_creation` 默认 `onceaday`：`pref_logging.xml:74`-`81`。
- 可选值为 `onceamonth`、`onceaday`、`everystart`、`custom`：`arrays.xml:3`-`15`。
- 偏好读取默认值也是 `onceaday`：`PreferenceHelper.java:764`-`778`。
- 文件名更新逻辑：
  - `onceamonth` -> `yyyyMM`
  - `onceaday` -> `yyyyMMdd`
  - `everystart` -> `yyyyMMddHHmmss`
  - `custom` -> 自定义模板，支持 `%year`、`%month`、`%day`、`%hour`、`%min` 等替换
  依据：`GpsLoggingService.java:881`-`908`、`Strings.java:299`-`328`。
- 真实文件不是启动时立刻创建，而是第一次写点时由 GPX/KML writer 在文件不存在时 `createNewFile()`：`Gpx10FileLogger.java:220`-`237`、`Kml22FileLogger.java:175`-`197`。

### 清理逻辑

- 手动删除 GPX/KML 等日志文件：`LoggingSettingsFragment.java:270`-`282`，在 `PreferenceHelper.getGpsLoggerFolder()` 下多选文件并调用 `f.delete()`。
- 自动发送只筛选同 basename 的文件并可生成 zip 上传，未删除源 GPX/KML：`FileSenderFactory.java:95`-`143`。
- 代码搜索未发现针对 GPX/KML 的按日期/容量/保留期自动删除逻辑。搜索命中删除点主要是手动删除、临时文件、GPX 注释改写旧文件。
- 本地轨迹缓存是另一套机制：默认开启，默认保留 24 小时；写入每 200 个点触发清理，进入轨迹地图和修改保留时间也会清理：`TrackCacheRepository.java:31`-`66`、`80`-`95`，`TrackMapViewFragment.java:677`-`685`，`TrackerSettingsFragment.java:70`-`77`。

## 方案取舍

### 问题 1：记录到 GPX/KML 哪个更省电

已确认：

- 只开一种格式比同时开 GPX+KML 更省，因为 `FileLoggerFactory` 会按启用项分别创建 logger 并逐个写：`FileLoggerFactory.java:64`-`75`、`107`-`109`。
- GPX 是默认开启，KML 默认关闭：`pref_logging.xml:7`-`25`。
- KML 每点写 `<when>` + `<gx:coord>`，GPX 每点写 `<trkpt>`；KML 文本略重，但两者都是本地文件追加，差异不是主要耗电来源。

建议：

- 如果没有 KML 消费需求，保留 GPX、关闭 KML。
- 真正省电应优先调大最小记录间隔/距离、关闭“保持 GPS 常开”、减少高精度重试、按需关闭自动上传；这些才直接影响定位和网络耗电。依据：`PreferenceHelper.java:340`-`412`、`GpsLoggingService.java:1209`-`1241`。

不可推断：

- 不能从代码静态判断 GPX 比 KML 具体省多少电，需要设备级 profiling。

### 问题 2：现在文件创建和清理逻辑

创建：

- 默认同一天同一 basename，GPX/KML 分别为 `yyyyMMdd.gpx` / `yyyyMMdd.kml`。
- 如果配置为每月、每次启动或自定义模板，则不再是一天一个。
- 同一天重复启动且仍是 `onceaday` 时，会继续写同名文件；是否产生新文件由文件名模式决定。

清理：

- GPX/KML 文件：有手动删除，无自动清理。
- 本地轨迹缓存：有自动清理和手动清空，但与 GPX/KML 文件无关。

### 问题 3：轨迹地图是否应直接取 GPX/KML 文件

不建议作为主方案，理由如下：

- **开关解耦**：用户可以关闭 GPX，也可能只开 Custom URL/KML/CSV；KML 默认就是关闭。轨迹地图若依赖 GPX/KML，会被日志格式开关影响。当前缓存由 `TrackCacheFileLogger` 纳入写入管线，开关独立为 `local_track_cache_enabled`，和 GPX/KML 是否启用解耦。
- **查询效率**：轨迹地图按时间窗查询，当前 SQLite 用 `recorded_at` 范围查：`TrackMapViewFragment.java:338`-`345`、`TrackPointDao.java:49`-`63`。GPX 现有 reader 用 DOM 解析整个文件并遍历全部 `trkpt`：`GpxReader.java:49`-`116`，不适合地图频繁刷新。
- **格式覆盖不足**：代码里有 `GpxReader`，未发现 KML reader；KML writer 的轨迹点是 `gx:Track`，若改读 KML 需要新增解析器。
- **跨文件复杂度**：文件可能按天/月/启动/自定义模板切分，地图默认时间窗可能跨多个文件，需要先发现、排序、解析、合并。
- **写读并发风险**：GPX/KML writer 会在闭合标签前 seek 写入；地图若同时解析正在写的文件，需要处理半写入和 XML 不完整状态。
- **字段损失**：`TrackPoint` 额外保留 provider、accuracy、speed、bearing、satellites、hdop/vdop/pdop、annotation、profileName、fileName、distanceMeters：`TrackPoint.java:6`-`24`。KML 轨迹主链路只写时间和坐标；GPX 也不能完整覆盖缓存字段。

可接受的折中：

- 保持 SQLite 本地轨迹缓存作为主数据源。
- 如需查看历史 GPX/KML，可做“导入/回填到缓存”的离线任务，而不是地图每次刷新直接解析文件。
- 如果必须从文件展示，优先只支持 GPX 作为 MVP，并限制扫描时间范围、后台解析、缓存解析结果；KML 另行评估。

### 问题 4：轨迹地图缓存是否应作为 FileLogger

结论：**应该把“本地轨迹缓存写入器”适配为 `FileLogger`，但不应把“轨迹地图视图”作为 `FileLogger`。**

理由：

- `FileLogger` 在现有项目里实际承担的是“定位点输出端”职责，不是严格的文件 writer；Custom URL、OpenGTS 也在同一工厂里，所以本地 SQLite 缓存作为内部输出端符合现有架构。
- 直接在 `FileLoggerFactory.write()` 写死 `TrackCacheRepository.getInstance().append(loc)` 会让新增链路成为特例；包装成 `TrackCacheFileLogger` 后，写入入口变为统一遍历 `FileLogger.write()`。
- `TrackCacheRepository` 仍保留缓存落库、查询、清理职责；`TrackCacheFileLogger` 只做适配，不把 UI、地图、数据库细节塞进工厂。
- `annotate()` 保持 no-op 是刻意设计：缓存写入发生在 `GpsLoggingService.writeToFile()` 清空 description 之前，`TrackCacheRepository.fromLocation()` 已从 `Session` 捕获 annotation；如果在 `annotate()` 再写一次会重复插点。
- 关于“为什么不将 `TrackCacheFileLogger` 放在 `getFileLoggers()`”：上一版不放的原因是当时没有「记录细节」显式开关，避免内部缓存项出现在 `GpsDetailedViewFragment` 的“记录到”展示中。现在已经在「记录细节」补齐同一个开关，因此更合理的方案是把它放进 `getFileLoggers()`，让它和 GPX/KML/Custom URL 一样成为用户可见、可开关的输出端。详情页展示调用依据：`GpsDetailedViewFragment.java:146`-`154`。

本轮实施：

- 新增 `gpslogger/src/main/java/com/mendhak/gpslogger/tracker/cache/TrackCacheFileLogger.java`。
- 修改 `gpslogger/src/main/java/com/mendhak/gpslogger/loggers/FileLoggerFactory.java`：`getFileLoggers()` 按 `local_track_cache_enabled` 加入 `TrackCacheFileLogger`，移除 `write()` 中对 `TrackCacheRepository.append()` 的直接调用。
- 修改 `gpslogger/src/main/res/xml/pref_logging.xml`：在「记录细节」增加 `local_track_cache_enabled` 开关。
- 修改 `gpslogger/src/main/java/com/mendhak/gpslogger/tracker/ui/TrackMapViewFragment.java`：关闭本地轨迹缓存时地图返回空点集。

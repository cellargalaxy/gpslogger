# 执行流程

> 流程冲突时以「任务 Prompt」为准。
> 关键结论/方案取舍/验证结果统一记录至`260704-204928-answer.md`(`prompt.md`路径相同)。

## 步骤

- 背景调研
    - 研读文档，对齐背景
    - 研读代码/IDL/配置，梳理核心逻辑/组件依赖/改动点
- 需求分析与方案
    - 提取核心目标/交付物/范围边界/关键约束
    - 制定方案：改动最小/复用优先；说明模块职责/输入输出/关键逻辑/异常处理
    - 评估对现有链路/性能/兼容性/下游的副作用
    - 写入`answer.md`：依据来源/方案取舍/实施步骤/验证说明
- 实施
    - 按方案执行，命名/注释/文案与项目风格一致
    - 中文注释与日志，处理边界与异常分支
    - 同步更新类型定义/关联配置/文档
- 验证与交付
    - 执行测试/逻辑校验/数据校验/文档校对
    - 核心产出同步至`answer.md`
    - 清理临时文件/调试代码/冗余产物，但无须提交变更

## 约束

- 依据：结论只能来自文档/代码/IDL/表结构/日志/SQL等明确来源；**严厉禁止猜测业务逻辑/捏造接口字段**。
- 引用：关键事实引用到具体章节/字段名/代码路径或枚举值，禁止笼统援引。
- 信息不足：区分「已确认/待确认/不可推断」并标注，不得脑补。
- 历史资料：历史Prompt/answer/旧方案仅供参考，必须与代码交叉核对后才能使用。
- 冲突：资料冲突时列出冲突点与采用依据，不得默默取一方。
- 风格：命名/注释语言/代码组织与项目既有风格一致，优先复用现有实现。

## 具体任务

+ 轨迹地图新增一个功能
+ 在地图顶部的「轨迹」下拉中，新增一个选择文件的按钮或者下拉选择框
+ 该按钮/下拉框，用于选择一个或者多个kml文件
  + 是采用文件选择按钮还是下拉框需要分析一下，各有好处
  + 文件选择按钮比较灵活，能选择任意位置的喀kml文件，但是每次选择文件会比较麻烦
  + 下拉框会预先加载可用的kml文件，不要手动在文件目录中翻找，比较方便，但是需要约定kml文件的存放路径
  + 目前我偏向是下拉框
+ 选择kml文件后，需要将kml文件中的路径展示到地图中
  + 需要注意kml文件路径需要能明显与历史路径区分开
  + 多个kml文件的路径之间也需要能明显区分开

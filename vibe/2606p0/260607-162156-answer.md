## 三、对原始疑问的直接回答

### 3.1 R2 关于补推点的时间

**结论：实时 Custom URL 链路的补推点时间即记录时刻，无需额外改造。**

证据：
- 入队时 `CustomUrlLogger.annotate()` 已经把当时的 `Location` 通过 `getFormattedTextblock()` 渲染好 URL/body/header（`CustomUrlLogger.java:81-99`），其中所有 `%timestamp / %time / %timeoffset / %date` 等占位符在入队当下就替换为该点的真实时间。
- 入队后存到 `WorkManager Data` 的是已经渲染好的字符串（`CustomUrlManager.java:158-167`）。Worker 真正执行 HTTP 时不会重新取「现在时间」，所以即便 6 小时后才补推，发出的内容仍是当时那一刻的时间和坐标。

**待加固点**：如果未来希望服务端能区分「记录时间」与「发送时间」，可在模板里同时暴露 `%recorded_at`（保留旧语义）和 `%sent_at`（Worker 真正发送时刻）。本次默认不引入，避免破坏向后兼容。

### 3.2 R6 关于 WorkManager 杀 App 是否丢点

**结论：当前实现下，`已成功入队 WorkManager` 的点跨进程被杀、被划掉、设备重启都不会天然丢失；但有三个明确的丢点边界，需要新增「本地补推外发队列」来覆盖旅行场景**。

确认：
- WorkManager 把已入队任务持久化在 App 私有 SQLite，跨 App 重启、跨设备重启会重新调度（Android 官方文档）。
- 当前 `setBackoffCriteria(EXPONENTIAL, 30s)` 与 `setRequiredNetworkRequest(...)` 决定：网络不可达时任务不会被调度（不会消耗重试次数），等到网络恢复才执行；这保证了「断网期间不会无谓失败重试」。

丢点边界（**这是历史草稿没明确指出但旅行场景务必注意的部分**）：
1. **重试上限只有 3 次**：`CustomUrlWorker.getRetryLimit() = 3`（`CustomUrlWorker.java:165-167`）。一旦联网后服务端 5xx 或网络抖动连续 3 次失败，该点会被 `Result.failure()` 永久丢弃，没有持久化的失败队列也没有用户手动重试入口。山区/弱网下这条边界很容易触发。
2. **`enqueueUniqueWork(tag, REPLACE, ...)`**：tag 来自 `Objects.hashCode(serializedRequest)`，理论上不同点 hash 不同；但若两个点序列化后完全一致（极少见但理论存在，例如静止点）后入队的会替换前者。
3. **请求尚未入队时进程被杀**：从 `LocationManager` 回调到 `enqueueUniqueWork` 之间的极短窗口里，进程被强杀会丢这一点（对应用户「可接受丢 1-2 点」的范围）。
4. **「丢弃离线位置」打开时**：当前实现在断网时直接 `return`（`CustomUrlLogger.java:71-74`），与 R2 诉求相反。需要在文档/UI 文案里明确：旅行场景必须保持该开关关闭。

**设计落地（必做）**：新增 `CustomUrlOutbox` 持久化外发队列（详见第六章 C），把「记录-入库-取出-发送」的状态全部落 SQLite。WorkManager 只承担「调度触发」职责，Worker 从 Outbox 里取消息发送；成功则删除该行，失败则记录 `attempt_count / last_error`，由 Outbox 自身负责重试（独立于 WorkManager 的 3 次上限）和最终失败留存。

### 3.3 R7 关于「为什么会需要批量补发 CSV 每一行」

**结论：CSV 批量补发不是 R2 的断网补推链路，而是另一条独立、可关闭的「自动发送回放」链路。本次需求不依赖它，且建议默认不启用，避免与新的本地补推队列产生重复发送。**

证据：
- CSV 批量只在「自动发送、发电子邮件和上传」启用、且「自动发送目标 = 自定义 URL」、且「记录细节 -> 记录为 CSV」三者同时打开时才会触发；触发点是 `CustomUrlManager.uploadFile()`（`CustomUrlManager.java:39-61`），它要求扫描出 `.csv` 文件。
- 当 R2 的实时 Custom URL 已经在断网期间排队、联网后补推时，再加上 CSV 自动发送等于把同一批点用第二条链路再发一遍。除非服务端按业务 ID 幂等去重，否则会重复入库。

操作建议：用户场景下，本需求只用「实时 Custom URL」+「Outbox」补推路径；`自动发送 -> 自定义 URL` 维持现状作为可选高级用法，不写入默认配置指引。

### 3.4 R11 关于地图 SDK 选型

**结论：不预先定 SDK，但给出明确候选与一周内可完成的 spike 方案。**

| 候选 | 许可证 | 维护状态 | 离线方案 | 风险点 |
| --- | --- | --- | --- | --- |
| MapLibre Native Android 11.x | BSD-2-Clause | 活跃 | `OfflineManager.createOfflineRegion(...)`、`OfflineTilePyramidRegionDefinition(styleURL, bounds, minZoom, maxZoom)` | 需选定矢量瓦片 / 样式 / tile source（OSM raster/MapTiler/自托管），瓦片来源可能有商用调用上限 |
| mapsforge + VTM | LGPL v3 + Android 例外 | 偏维护期，2024-04 后无新版 | 直接加载 `.map` 离线矢量地图文件，可整区域一次拷贝 | UI/渲染集成成本相对高，瓦片需通过 Mapsforge `map-writer` 自行预生成 |
| osmdroid | Apache-2.0 | 已归档（2024-11-20） | 内置 SQLite 瓦片缓存 + `MapTileDownloader` | 不再有官方更新，依赖 OSM 公共 tile 服务（有 user-agent / 流量政策限制） |

硬性约束：开源、无 Google Play Services 依赖、支持离线、与 GPLv2 项目兼容。

- BSD-2-Clause（MapLibre）与 GPLv2 兼容（GPL 允许吸收宽松许可证代码）。
- LGPL v3 在 Android 上需保证用户能替换库；mapsforge 官方说明含 Android 例外，可在 Android APK 内静态链接，不要求 App 自身开源。GPLv2 项目通常仍可携带 LGPLv3 库（运行时链接、提供替换通道）；建议在 spike 时让法务/owner 再确认。
- osmdroid Apache-2.0 与 GPLv2 兼容。但归档维护风险高，作为「最后兜底」。

Spike 任务（建议落到一个独立 Android 模块或独立分支，不污染主线）：
1. 接入 MapLibre Native 11.x，加载 `https://demotiles.maplibre.org/style.json`，画一条本地轨迹线，创建一个 30km × 30km、缩放 8-15 的离线区域并断网验证。
2. 接入 VTM，加载本地 `germany.map` 或类似离线文件，画轨迹线。
3. 对比指标：APK 体积增量、最低 Android 版本、首屏冷启动、离线 region 创建/列出/删除 API 完备度、瓦片源选择灵活度。
4. 一周内决定主选，备选作为降级方案。

## 四、目标与范围

### 4.1 目标

让 GPSLogger 在旅游徒步弱网/断网场景下：
- 不丢点：所有有效 GPS 点都能可靠地、按真实记录时间补推到 Custom URL；
- 可回查：用户能在 App 内立刻看到过去 N 小时的轨迹地图；
- 可离线看图：用户能预先下载关心区域的地图瓦片/矢量瓦片，断网下也能看到底图；
- 可管理：用户能直观管理「本地轨迹缓存」「地图数据缓存」「待补推队列」三者各自的容量。

### 4.2 范围内

- Custom URL 实时链路加固（本地 Outbox 持久化、独立重试、模板时间语义保持不变）。
- 新增「本地轨迹缓存」存储 + 自动清理。
- 新增主界面视图「轨迹地图」+ 按自然钟点切段着色。
- 新增「地图缓存管理」二级界面：列出/下载/删除离线区域。
- 新增设置项：本地轨迹保留时间、轨迹切段粒度、地图缓存上限、Outbox 重试策略。
- 可选：新增「待发送请求」管理视图（与 Outbox 联动）。
- 多语言：英文（默认）+ 简体中文。

### 4.3 范围外

- 不替换现有 GPX/KML/CSV/NMEA/OpenGTS/Email/SFTP/Dropbox/Drive/owncloud/OSM 等已有功能。
- 不修改 Custom URL 模板占位符语义（保持向后兼容）。
- 不引入 Google Play Services、Firebase、Google Maps SDK。
- 不引入 Kotlin（除非 SDK 强制要求；先维持 Java 主语言风格）。
- 不在后台自动下载地图数据。

## 五、关键约束与原则

1. **最小侵入**：所有新增能力以独立 package（如 `tracker.localcache`、`tracker.outbox`、`tracker.map`、`ui.fragments.map`）组织；尽量复用 `PreferenceHelper / Session / Systems / WorkManager` 现有基础设施。
2. **持久化优先用 SQLite**：与现有项目风格一致（项目目前未引入 Room），用 `SQLiteOpenHelper`；统一封装 DAO。
3. **不破坏 Custom URL 模板向后兼容**：模板字段、占位符语义不变。
4. **隐私**：所有新数据只落本机；提供清空入口；文案上说明「不会上传到第三方」。
5. **电量优先**：地图渲染只在打开「轨迹地图」时进行；瓦片下载必须用户手动触发；本地轨迹写入只做轻量插入。
6. **i18n**：所有新增字符串必须在 `values/strings.xml` 与 `values-zh-rCN/strings.xml` 同步落地；设置项 `key` 命名沿用 snake_case，统一前缀 `local_track_` / `track_map_` / `customurl_outbox_` / `offline_map_`。
7. **错误旁路**：本地缓存写入失败、地图加载失败、Outbox 入库失败都不得阻断 Custom URL 实时发送和原有 GPX/CSV 写入。
8. **可关闭**：所有新功能必须可在设置里关闭。默认值在「设置项默认值」一节明确。

## 六、方案设计

### A. 本地轨迹缓存（满足 R3、R9、R13）

**职责**：把通过过滤后的有效 `Location` 旁路写入一张 SQLite 表，供「轨迹地图」消费，并按保留时间自动清理。完全独立于 GPX/CSV/Custom URL 三条主链路。

**触发点**：在现有 `GpsLoggingService`（或与 `FileLoggerFactory.write` 同一调用层）处增加 hook，把 `Location loc` 投递到 `TrackCacheRepository.append(loc)`。

**数据模型**：`local_track_points`
- `id` INTEGER PRIMARY KEY AUTOINCREMENT
- `recorded_at` INTEGER NOT NULL（毫秒时间戳，即 `Location.getTime()`）
- `inserted_at` INTEGER NOT NULL（本地入库时刻，便于诊断时序）
- `lat` REAL NOT NULL
- `lon` REAL NOT NULL
- `altitude` REAL
- `accuracy` REAL
- `speed` REAL
- `bearing` REAL
- `provider` TEXT
- `satellites` INTEGER
- `hdop`/`vdop`/`pdop` REAL
- `annotation` TEXT
- `profile_name` TEXT
- `file_name` TEXT
- `distance_meters` REAL（与 `Session.getTotalTravelled()` 对应）
- INDEX `idx_local_track_points_recorded_at(recorded_at)`

**清理策略**：
- 触发时机：App 启动、写入后每满 200 点、用户打开「轨迹地图」、用户改保留时间设置后立即触发一次。
- 清理 SQL：`DELETE FROM local_track_points WHERE recorded_at < (now - retentionMs)`；空间不足兜底再按 `recorded_at` 升序删除最旧 N 条。
- 完全关闭本地缓存时：用户手动「清空所有本地轨迹」按钮 + 自动停止写入。

**异常处理**：
- 写入失败：仅 `LOG.debug`，不影响主链路。
- 数据库锁/磁盘满：捕获 `SQLiteException`，触发一次清理，再失败则跳过该点。

**性能预算**：写入间隔 ≥ 现有 GPS 采样间隔（一般 ≥ 5 秒），单次 INSERT < 5ms。

### B. 轨迹地图视图（满足 R4、R5、R8）

**职责**：在主界面 Spinner 增加第 6 个视图「轨迹地图」。展示本地轨迹缓存中、最近一个时间窗（如保留时间内或用户选定时间范围内）的轨迹线，按自然钟点边界切段并按段着色，叠加在离线/在线底图之上。

**新增 Fragment**：`com.mendhak.gpslogger.ui.fragments.display.TrackMapViewFragment`，继承 `GenericViewFragment`。

**注册点**：
- `gpslogger/src/main/res/values/arrays.xml` 在 `gps_main_views` 末尾新增 `@string/view_track_map`。
- `gpslogger/src/main/res/values/strings.xml` 增 `view_track_map = "Track Map"`；`values-zh-rCN/strings.xml` 增 `view_track_map = "轨迹地图"`。
- `GpsMainActivity.loadFragmentView(int)` 增加 `case 5:` 加载 `TrackMapViewFragment.newInstance()`。
- 旧偏好 `userSelectedNavigationItem` 是 int，需要在迁移逻辑里做兼容（≤4 保持，新增 5）。

**时间切段算法**（明确且可单元测试）：
```
segmentMillis = userSelected (5/10/15/30/60 分钟，毫秒)
对每个点 p:
    segmentIndex = floor(p.recorded_at / segmentMillis)
当 segmentIndex 发生变化时换色；相邻两点跨越边界时，在边界处线性插值出一个边界点用于绘制颜色切换，但不写回 SQLite。
```
- 示例（R5 中给出的）：粒度 15 分钟、轨迹 13:12 ~ 13:33 → 段 1 `13:12~13:15`，段 2 `13:15~13:30`，段 3 `13:30~13:33`。
- 颜色环：使用 8-12 种区分度高的颜色循环（HSL 等间距生成）；不与底图主色冲突。
- 图例：底部固定 chip 列表，显示每段「起 - 止 时间 / 颜色」。

**交互**：
- 打开后默认时间范围 = 保留时间窗（默认 24h）；提供「30 分钟 / 2 小时 / 6 小时 / 12 小时 / 24 小时 / 自定义」快速过滤。
- 「定位到最新点」按钮：相机移到最新点。
- 「适应轨迹边界」按钮：相机适配 bounding box。
- 「刷新」按钮：从 SQLite 拉最新点。
- 切段粒度从设置页或地图工具栏改都能即时生效。
- 无底图降级：地图 SDK 报错或当前位置无离线包时，依然在纯色背景上绘制轨迹线，并提示「该区域底图未缓存」。

### C. Custom URL Outbox（满足 R2、R6）

**职责**：用本地 SQLite 表替代「直接把请求塞进 WorkManager Data」的做法，作为唯一可信的待发送队列。WorkManager 只作为调度入口。

**数据模型**：`customurl_outbox`
- `id` INTEGER PRIMARY KEY AUTOINCREMENT
- `recorded_at` INTEGER NOT NULL（点的真实记录时间）
- `created_at` INTEGER NOT NULL（入 outbox 时间）
- `url` TEXT NOT NULL（已渲染）
- `method` TEXT NOT NULL
- `headers` TEXT NOT NULL（已渲染，可含敏感信息，需考虑 DB 加密：可选 SQLCipher，但首版先不强制以减依赖）
- `body` TEXT NOT NULL（已渲染）
- `basic_auth_username` TEXT
- `basic_auth_password` TEXT
- `status` TEXT NOT NULL CHECK(status IN ('PENDING','IN_FLIGHT','FAILED','SUCCEEDED'))
- `attempt_count` INTEGER NOT NULL DEFAULT 0
- `last_error` TEXT
- `last_attempt_at` INTEGER
- `next_attempt_at` INTEGER
- INDEX `idx_customurl_outbox_status_next(status, next_attempt_at)`

**流转**：
1. `CustomUrlLogger.annotate()` 完成模板渲染后，调用 `OutboxRepository.enqueue(...)` 写入 `PENDING`。
2. 写入成功后调度一次 WorkManager（`CustomUrlOutboxWorker`，网络约束依然按 `shouldAutoSendOnWifiOnly()` 决定）。
3. `CustomUrlOutboxWorker.doWork()`：
   - 取所有 `status=PENDING AND next_attempt_at <= now` 的行，按 `recorded_at ASC` 顺序逐条发送。
   - 单条成功：行更新为 `SUCCEEDED` 并归档/物理删除（默认物理删除；可由设置「保留已发送请求 X 天」改成软删除）。
   - 单条失败：`attempt_count += 1`；若 `attempt_count < maxAttempts` 写回 `PENDING` + 退避计算下次时间；若 ≥ `maxAttempts` 写 `FAILED`，停止再试，等待用户手动重试。
4. 网络断开期间任务不会被调度（约束未满足），所以「重试次数」只在能联网时消耗，与「断网时间」无关。
5. 启动 App 时如果 Outbox 还有 `PENDING`，立刻调度一次。

**重试与退避**：
- 默认 `maxAttempts = 16`，远高于现有的 3，足够覆盖一天间歇性服务端抖动。
- 退避：指数 30s → 60s → 120s → ... 上限 1 小时；同时尊重 `Retry-After` 响应头（如果存在）。

**清理与上限**：
- 设置「Outbox 最大行数」防止极端情况下无限增长（默认 200000 行；按 1 点/秒 ~ 55 小时，远超旅行所需）。超出时按 `recorded_at` 升序删除最老的 `PENDING` 行并落 `WARN` 日志。
- 设置「已发送行保留时间」（默认立即删除）。
- 设置「失败行最长保留」（默认 30 天）。

**兼容性**：
- 不改变 Custom URL 模板占位符语义。
- 不再走 `CustomUrlManager.sendByHttp()` 直接入 WorkManager Data 的旧路径；旧路径转为内部调用 `OutboxRepository.enqueue(...)`，对调用方透明。
- 现有 CSV `自动发送` 链路（FileSender）不动，但需要在文案里明确「与 Outbox 是两套路径」。

### D. 地图数据缓存与管理界面（满足 R10、R12）

**职责**：让用户能在有网时主动下载一个区域的地图数据，断网后查看；并能管理已下载内容。

**入口**：
- 主菜单「设置」下新增「离线地图缓存」二级页面。
- 「轨迹地图」工具栏放一个 shortcut「下载当前视野」。

**核心能力（与 SDK 抽象隔离）**：定义 `OfflineMapStore` 接口：
- `listRegions(): List<OfflineRegion>`
- `createRegion(name, bounds, minZoom, maxZoom): RegionId`
- `getProgress(regionId): Flow<Progress>`（Java 项目无 Flow，可用 EventBus + 状态回调）
- `cancel(regionId)` / `resume(regionId)`
- `delete(regionId)`
- `totalBytes(): Long`
- `lastUsedAt(regionId): Long`
- 由 `MapLibreOfflineMapStore`（首选）或 `VtmOfflineMapStore`（备选）实现。

**UI 列表**：
- 名称（默认按下载时间生成，可重命名）
- 边界（经纬度框）
- 缩放级别
- 大小 / 进度
- 下载时间 / 最近一次被加载时间
- 操作：取消、重试、删除、定位

**创建缓存的来源**：
- 当前视野（首版必做）。
- 当前位置周边 5/10/20km 圆形（首版可选；圆形换算为外切矩形也可）。
- 手动框选（首版可选，复杂度高，可放二阶段）。

**配额与清理**：
- 默认「单 App 离线地图总占用上限 1GB」，可由设置项 `offline_map_max_bytes` 调整。
- 用户可手动按区域删除。
- 不在 UI 自动按 LRU 删除，避免用户出发前临时清掉关键区域；只显示「最近使用时间」作为参考。

**离线降级行为**：
- 当前位置无对应离线区域时，「轨迹地图」上方提示「该区域底图未缓存，仅显示轨迹」。
- 轨迹线照常绘制（不依赖底图）。

| 现有能力 | 是否改动 | 说明 |
| --- | --- | --- |
| GPX/KML/CSV/NMEA/GeoJSON 写入 | 不改 | 与本地轨迹缓存解耦 |

| 「自动发送间隔」 | 不改 | 与 Outbox 不冲突 |

### 兼容性

- 偏好 key 新增不与现有冲突。
- 数据库与现有不冲突：新增独立 `gpslogger_tracker.db`（与 Custom URL Outbox 共享一个 DB 文件、不同表）。
- APK 体积：MapLibre Native 预估 +5~10MB（含必要 native so）；VTM 预估 +3~6MB。需在最终选型时确认。
- 最低 SDK：项目 `minSdkVersion 21` 与两种 SDK 都兼容。
- F-Droid 构建：MapLibre Native 在 Maven Central，VTM 在 jitpack；F-Droid 可构建，需验证 reproducible-build 元数据。

### 性能 / 电量

- 本地轨迹写入：单点 < 5ms，可忽略。
- Outbox 写入：单点 < 10ms。
- 地图渲染：只在「轨迹地图」展示时启用，进入其他视图时销毁 MapView。
- 离线下载：用户手动触发；下载过程显示进度条 + 取消按钮。

### 隐私

- 所有新增数据均存 App 私有目录，未授权时不可被其他 App 读取。
- 提供「清空所有本地轨迹」「清空所有离线地图」「清空 Outbox」三个独立入口。
- 文案：明确「数据仅在本机，不会自动上传」。

## 十、验证说明

### 10.1 单元测试要覆盖

- 切段算法：13:12~13:33 / 15 min；00:14 / 5 min；23:58 跨日；空轨迹；单点。

# 旅游徒步改造需求设计

生成时间：2026-06-07

用户补充：实际使用的是 Custom URL，App 使用简体中文界面；代码实际开发时配置和文案需要同时支持英文与中文。本文档用中文描述，便于复核。

## 结论摘要

- Custom URL 主路径不需要 CSV：如果启用 `记录细节` -> `记录到自定义 URL`，并保持 `丢弃离线位置` 关闭，断网时每个点会进入 WorkManager 等待联网后补推。此前提到的“批量补发 CSV 每一行”只是 Custom URL 的另一种 `自动发送` 模式，不是本需求默认方案。
- 已确认：Custom URL 补推使用记录时的位置时间。实时 Custom URL 请求基于原始 `Location` 格式化；CSV 批量模式也会从 `timestamp_ms` 恢复 `Location.setTime(...)` 后替换 `%timestamp`、`%time`。
- 明确新增：主界面新增 `轨迹地图` 视图，展示本地轨迹缓存，并按 5/10/15/30/60 分钟切段上色。
- 明确新增：本地轨迹缓存默认保留 `24 小时`，必须自动清除超过缓存时间的数据。
- 明确新增：地图数据缓存/离线地图能力。用户应能在有网时提前下载地图数据，之后无网查看；还需要管理界面查看已缓存范围、触发下载、清理无用缓存。
- 地图 SDK 选型暂不定。必须开源、无 Google Play Services 依赖、支持离线/预下载；`osmdroid` 因官方仓库已归档，不再作为默认推荐。
- 可选增强：如果实现不复杂，可新增面向用户的 Custom URL 队列管理视图，用于查看待补推/失败请求并手动重试或清理。

## Custom URL 配置结论

### 实时逐点发送（默认推荐）

配置路径使用中文界面名称：

- 进入 `记录细节`，启用 `记录到自定义 URL`。
- 进入 `自定义 URL` 设置页，配置 `URL`、`HTTP 方法`、`HTTP 头`、`HTTP 内容`、`基础认证`。
- 保持 `丢弃离线位置` 关闭。这样断网时请求等待联网后补推。
- 如果旅行中经常只有蜂窝网络，不建议启用 `仅在 Wi-Fi 环境下发送`，否则补推会等到 Wi-Fi。

这条路径不需要 CSV。CSV 不是断网补推的前置条件。

### Custom URL 的 CSV 批量模式（可选，不是默认）

`自动发送、发电子邮件和上传` -> `允许自动发送` -> `自动发送目标` -> `自定义 URL` 会启用另一条批量链路：从 CSV 文件逐行生成 Custom URL 请求。

这个模式适合这些场景：

- 想按固定周期批量回放整个文件。
- 服务端已有幂等能力，能按 `%timestamp` 或业务 id 去重。
- 想额外保留 CSV 作为人工排错或服务端重建数据来源。

它不适合作为本需求默认方案，因为实时 Custom URL 队列已经能覆盖“断网缓存、恢复联网补推”。批量 CSV 还可能重复发送同一文件里的旧点，服务端必须去重。

## WorkManager 持久化与杀 App 行为

结论：已成功 enqueue 到 WorkManager 的 Custom URL 请求会持久化，不会因为普通进程被系统杀掉或用户从最近任务划掉而天然丢失；但它不是完整业务队列表，仍有边界。

已确认依据：

- Android 官方文档说明 WorkManager 适合 App 离开可见状态后仍需可靠执行的任务，任务会跨 App 重启和设备重启持久化。
- Android 官方文档说明已调度 work 存在 WorkManager 内部 SQLite 数据库中，并会在设备重启后重新调度。
- 当前代码 `Systems.startWorkManagerRequest()` 使用 `OneTimeWorkRequest`、网络约束和 `enqueueUniqueWork(...)`。Custom URL 实时发送通过 `CustomUrlManager.sendByHttp()` 把格式化后的 URL/body/header 序列化进 WorkManager `Data`。

不同“杀 App”场景：

- 普通系统回收进程：已入队 WorkManager 任务保留，联网后会继续调度。
- 从最近任务划掉：标准 Android 行为下通常不等于强行停止，已入队任务仍应保留；但部分厂商 ROM 会把划掉当作 force-stop 处理。
- 设备重启：WorkManager 设计上会重新调度已持久化任务。
- 系统设置里点“强行停止”：App 进入 stopped state，WorkManager/JobScheduler/Alarm 等都不能运行；任务数据通常仍在 App 私有数据库里，但要等用户再次打开 App 后才有机会恢复调度。
- 清除应用数据或卸载：WorkManager 内部数据库和待发送请求都会被删除。
- 请求尚未 enqueue 成功时进程崩溃：这一点可能丢，因为还没进入持久化层。

当前实现的额外边界：

- WorkManager `Data` 是轻量输入，不适合作为业务数据仓库；官方 API 对序列化后的 `Data` 有大小上限。Custom URL 单点请求一般够用，但长 body/header 或未来扩展字段过多时有风险。
- 当前代码用 `enqueueUniqueWork(tag, ExistingWorkPolicy.REPLACE, workRequest)`。实时 Custom URL 的 tag 来自序列化请求 hash，通常每个点不同；但理论上完全相同的请求会互相替换。
- WorkManager 能告诉任务状态，但不天然提供面向用户的业务队列管理、请求内容审计、过期清理策略。

设计结论：

- 若只要求“断网后尽量可靠补推，杀普通进程不丢”，当前 WorkManager 方案基本够。
- 若要求“旅行场景下尽量不丢点、用户可查看待补推队列、强停后打开 App 能明确恢复、可重试失败请求”，应新增 `CustomUrlOutbox` 表：记录请求内容、记录时间、状态、重试次数、最后错误、下次重试时间；Worker 只消费 Outbox。这样 WorkManager 只负责调度，业务数据由我们自己的 SQLite 持久化。

## 新增能力设计

### A. 本地轨迹缓存

目标：

- 记录到的有效点，在 Custom URL 发送之外，额外写入 App 本地轨迹缓存。
- 缓存用于 `轨迹地图`，与 GPX/CSV 开关解耦。即使只启用 `记录到自定义 URL`，地图也能显示最近轨迹。
- 默认保留 `24 小时`。
- 必须自动清除超过缓存时间的数据。

推荐设置：

- 新增设置项：`本地轨迹保留时间`。
- 默认值：`24 小时`。
- 候选值：`1小时 / 3小时 / 6小时 / 12小时 / 24小时 / 3天 / 7天`。
- 代码需要同时补英文默认资源 `values/strings.xml` 和简体中文资源 `values-zh-rCN/strings.xml`。

数据职责：

- `TrackCacheRepository`：接收通过现有过滤后的有效 `Location`，落盘为结构化点。
- `TrackCacheCleaner`：按保留时间清理过期点。
- 自动清理触发点：App 启动、每次插入轨迹点后、打开 `轨迹地图` 时、保留时间设置变更后。
- `TrackPoint` 字段：记录时间、经纬度、海拔、精度、速度、方向、provider、卫星数、HDOP/VDOP/PDOP、注释、profile、文件名、累计距离、写入时间。

存储取舍：

- 推荐先用 `SQLiteOpenHelper`，不引入 Room，保持当前 Java 项目的依赖风格。
- 不建议直接解析 GPX/CSV 做地图数据源。原因：用户可能关闭这些格式；跨文件模式、CSV 分隔符和大文件解析会让地图打开变慢。

异常处理：

- 缓存写入失败不阻断 Custom URL 发送和现有文件记录。
- 磁盘不足时先自动清理过期轨迹点；仍失败则跳过本点缓存，并记录 debug log。

### B. 轨迹地图视图

目标：

- 新增主界面视图：`轨迹地图`。
- 显示本地缓存中的最近轨迹。
- 支持用户配置切割粒度：`5分钟 / 10分钟 / 15分钟 / 30分钟 / 60分钟`。
- 按自然时间边界切段并用不同颜色展示。

切段规则：

- 使用记录时间 `recorded_at`，不是插入时间、补推时间或服务器接收时间。
- 边界按自然钟点对齐：`floor(recorded_at / segmentMillis) * segmentMillis`。
- 示例：粒度 15 分钟，轨迹 13:12 到 13:33，切为 `13:12~13:15`、`13:15~13:30`、`13:30~13:33`。
- 若相邻两个点跨越边界，展示层可插值边界点用于绘制颜色切换，但不写回缓存。

交互范围：

- 打开后自动缩放到最近轨迹边界。
- 支持回到最新点、缩放、刷新。
- 图例显示每段起止时间与颜色。
- 即使无网络、底图不可用，也必须能绘制轨迹线和点。

### C. 地图数据缓存与管理界面

目标：

- 支持有网时提前下载地图数据，之后无网查看。
- 新增管理界面，用于查看、下载、清理地图缓存。

管理界面至少包括：

- 已缓存区域列表：名称、边界范围、缩放级别、大小、下载时间、最近使用时间。
- 创建缓存：可基于当前地图视野、当前位置周边半径、或手动框选区域。
- 下载控制：开始、暂停/取消、失败重试、显示进度和预计大小。
- 清理：删除单个区域、删除全部地图缓存、按最近使用时间清理。
- 存储提示：显示地图缓存占用空间，与本地轨迹点缓存分开统计。

离线行为：

- `轨迹地图` 优先使用已下载地图数据。
- 缺少底图时不应阻塞轨迹显示；只提示“该区域地图未缓存”。
- 地图缓存清理不应删除本地轨迹点；本地轨迹点清理也不应删除地图瓦片/离线包。

### D. Custom URL 队列管理视图（可选）

如果复杂度可控，建议新增一个面向用户的队列管理视图：

- 查看待发送、发送中、失败、已成功的 Custom URL 请求数量。
- 查看失败原因和最后重试时间。
- 手动重试失败请求。
- 删除失败或过期请求。

注意：当前 WorkManager 队列并不是为这种细粒度用户管理设计的。若要做得清楚，可能需要新增一层 `CustomUrlOutbox` 表，把请求状态持久化，再由 Worker 消费。

## 地图 SDK 选型

结论：暂不直接定 `osmdroid`。需要做一个技术 spike 后再定。

硬性条件：

- 开源。
- 无 Google Play Services 依赖。
- 支持 Android 原生视图嵌入。
- 支持提前下载地图数据并离线使用。
- 能画轨迹线、点、分段颜色和图例交互。
- License 与当前 GPL 项目兼容。
- 维护状态可接受，至少最近仍有版本或活跃维护。

候选方向：

- `MapLibre Native Android`：优点是开源、Native、支持离线区域 API、维护状态较好；风险是要选定样式和瓦片来源，离线区域管理、下载大小控制、tile source 授权要设计清楚。
- `mapsforge` / `VTM`：优点是偏离线地图文件，适合完全离线查看；风险是 UI/渲染和当前项目集成成本、地图数据来源、样式能力需要验证。
- `osmdroid`：不作为默认推荐。原因是官方仓库已归档，维护风险较高；除非 spike 证明它仍是最小可行且风险可接受，否则不选。
- 直接复用 Organic Maps/CoMaps/OsmAnd 这类完整 App 代码不建议作为第一方案，体量和集成边界太大；但可以参考其离线地图产品形态。

Spike 建议：

1. 用 MapLibre Native 做最小 demo：显示 OSM/自托管矢量瓦片、画轨迹线、创建离线区域、列出/删除离线区域。
2. 用 mapsforge/VTM 做最小 demo：加载本地离线地图文件、画轨迹线、验证文件大小和下载来源。
3. 对比 APK 体积、许可证、最低 Android 版本、离线下载 API、缓存可管理性、F-Droid 构建风险。
4. 再决定最终 SDK。

## 副作用与兼容性

- 存储：新增轨迹缓存和地图数据缓存都会占用空间，需要分开统计和清理。
- 隐私：本地缓存会保存近期轨迹。设置文案要明确“仅保存在本机，超期自动删除”。
- 上传链路：新增轨迹缓存和地图缓存不改变现有 Custom URL 发送语义。
- 电量：记录后台只写轻量本地缓存；地图渲染和地图下载只在用户打开相关界面或明确触发下载时执行。
- 网络：地图数据预下载必须由用户主动触发或明确配置，不应在后台偷偷下载大区域。
- 多语言：代码新增配置必须使用 string resource，至少补英文 `values/strings.xml` 和简体中文 `values-zh-rCN/strings.xml`。
